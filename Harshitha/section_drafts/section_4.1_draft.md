# 4.1 Architecture, storage, and query processing

MongoDB’s architecture is best understood as the interaction of three parts: the document model exposed to applications, the server components that interpret and plan requests, and the storage engine that reads and persists data. The document model gives applications a flexible way to represent related information, while the query layer translates requests into operations over collections and indexes. Beneath that layer, WiredTiger manages in-memory and on-disk data. These parts work together, but they should not be treated as interchangeable: the query planner chooses how a request will be executed, whereas the storage engine is responsible for managing the data used by that execution [15]–[17].

At the application boundary, MongoDB clients use language-specific drivers to submit operations to the server. Queries are represented in BSON and operate on documents in collections. A request such as `find()` can specify conditions and, where required, projection, sorting, or limits. The aggregation interface provides a sequence of stages for filtering and transforming documents. This gives application developers a common way to express data access, but it does not determine by itself which physical access path will be fastest. That decision belongs to query planning [13], [15].

For queries that require optimization, MongoDB first interprets the request and forms a normalized representation, often described in the literature as a query shape. The planner can then generate candidate execution plans using the available indexes and applicable query operations. A plan is represented as a tree of stages: the upper stages describe work such as filtering or returning results, while the leaves obtain documents through an index or a collection scan. The server evaluates candidate plans, selects one for execution, and may cache the choice for later queries of the same shape. Normalizing queries makes plan reuse possible across requests whose literal predicate values differ, although the concrete values remain relevant to evaluating a particular request [13].

The precise selection mechanism depends on the MongoDB version and the query. Tao et al. describe the first-past-the-post (FPTP) optimizer in MongoDB 7.0.1. In the tested mechanism, candidate plans are advanced in a trial period and scored using their observed progress and work. The winning plan is then run to completion. This is different from estimating the total cost of every possible plan before execution. Current MongoDB documentation describes more than one selection mechanism; for eligible queries in MongoDB 8.3, a cost-based ranker can act as a backup to multi-planning. The FPTP account should therefore be cited as a version-specific description, not as a timeless description of MongoDB’s query planner [13], [18].

The paper’s experiments illustrate why this distinction matters. Using MongoDB 7.0.1, Tao et al. tested simple conjunctive range queries over a collection of 100,000 documents with two indexed integer fields. In that setup, the optimizer selected between index-scan plans but did not include a collection scan as a candidate in the cases studied. The authors report plan-selection accuracy below 34% and an average impact factor of 1.7 for their workload. Those measurements show that a plan chosen by the optimizer can be slower than the best plan identified for that test; they do not establish that MongoDB is generally inaccurate or slow. The experiment uses a narrow workload and does not cover complex aggregation, disjunction, or cross-collection lookup queries [13].

Once a plan requests data, the storage engine handles its representation in memory and on disk. WiredTiger is the default storage engine for current MongoDB deployments covered by the manual, although the documentation identifies deployment-specific exceptions. The WiredTiger architecture guide describes data organized in B-trees and pages, with components for caching, eviction, block-based file access, checkpoints, history, and recovery. MongoDB’s current manual also describes WiredTiger’s use of multi-version concurrency control (MVCC), point-in-time snapshots, document-level write concurrency, and optimistic conflict handling. These mechanisms allow operations to work with consistent views of data while concurrent work proceeds; they also mean that storage behavior can affect the amount of work and latency observed by a query [16], [17].

Durability involves both checkpoints and journaling. A checkpoint records a consistent state of data files, while the write-ahead journal records changes made since the relevant checkpoint. Following an unclean shutdown, recovery can replay journaled changes to restore the database to a consistent state. This provides essential context for understanding how MongoDB persists updates, but the detailed behavior depends on storage-engine configuration and server version. The WiredTiger architecture guide itself cautions that its internals documentation may not be complete or synchronized with every code release, so current operational claims should be checked against the MongoDB manual and the corresponding source version [16], [17].

The sources also clarify the boundary between query abstraction and internal query processing. Cabral et al. propose expressing retrieval queries over an Entity–Relationship model and generating MongoDB-native queries from a mapping to the physical document schema. Their work is relevant because it shows how data layout can change the generated query and the operations needed to retrieve related data. It addresses how developers specify and generate queries, however, rather than how MongoDB’s internal optimizer selects a plan. Similarly, MongoDB’s Architecture Guide presents the document model and Query API as product-level architectural foundations, but it is a vendor white paper and does not provide an independent evaluation of query performance [14], [15].

Taken together, the evidence supports a layered account of MongoDB’s architecture: applications express document-oriented requests; the server interprets and plans eligible queries; and WiredTiger manages the underlying data and persistence. Query performance depends on the request, data distribution, indexes, selected plan, storage behavior, and MongoDB version. The available research offers a detailed view of plan selection for a limited MongoDB 7.0.1 workload, while the official documentation explains storage-engine mechanisms and current version-specific behavior. Neither should be generalized beyond its stated scope.
